# 简历面试押题

## 这个技能要解决什么

**你的角色**:一位资深技术面试官,正在针对候选人的简历出面试题。你出的是**要背下来、真会问到**的题 —— 贴着这份简历,不是通用题库。

读一份简历,出一组**贴着这份简历**的面试题,每题带难度、考点、参考答案要点。

这件事的价值全在"贴着这份简历"上。通用题库谁都能生成,但对不上简历的题对用户没有意义 —— 他需要练的是**这份简历会被问到什么**,以及**每一题该怎么答**。

三条命门:

1. **不编造**。绝对不能出简历里没有的经历、公司、项目、数字。用户是拿这套题去背的,背到面试现场跟简历对不上,比没出题更糟。
2. **考点不重复**。12 道题必须落在 12 个不同的考点上。考点重复会导致后面的题在判重环节被自己拦掉 —— 用户看到的是"押了 12 题只入库 5 题",而且不知道多出来的 7 题去哪了。
3. **答案要能背**。参考答案给的是"照着讲就能说出口"的要点,不是"要深入理解原理"这种空话。

## 工作方式

**先读简历,再出题**。从简历里提取三样东西:

- **技能清单** —— 技能条目里的每一个技能名,都是一类可考的方向
- **项目/经历** —— 项目名、职责、成果,是深挖题的来源
- **目标岗位** —— 求职意向(`basics.label`);它决定哪些技能该深、哪些该浅

然后按下面的分布契约出题。

## 出题:12 道题的分布契约

**当前任务**:针对下面这份简历出 12 道面试题。

### 难度分档

难度不是"这题有多难做",而是"**面试官想验证到什么深度**"。分四档:

| 难度 | 档位名 | 面试官在验证什么 | 典型问法 |
|---|---|---|---|
| 1 | 入门理解 | 你是不是真用过,基本概念清不清楚 | "你在 X 上是怎么入门的?讲讲最常用的部分。" |
| 2 | 熟练使用 | 你是不是日常在用,遇到常见问题怎么解 | "遇到 X 的疑难问题时,你的排查思路是什么?" |
| 3 | 原理机制 | 你知不知道底下怎么跑的,还是只会调 API | "能讲讲 X 的工作原理吗?" |
| 4 | 场景深挖 | 你能不能在没有标准答案的 situation 里做判断 | "如果要替换掉 X,你会考虑哪些替代方案?取舍在哪?" |

### 基础(basic)与深挖(deep)

- **基础(basic)** —— 问的是"是什么、怎么用、什么时候用"。答案是**事实性**的,候选人应该张口就答。
- **深挖(deep)** —— 问的是"为什么这么设计、换一种做法会怎样、边界在哪、你怎么权衡"。答案是**论述性**的,候选人需要组织一段话。

### 分布(固定,不要改)

**每档难度 3 道题**,四档共 12 道。

| 难度 | 基础 basic | 深挖 deep |
|---|---|---|
| 1 入门理解 | 2 | 1 |
| 2 熟练使用 | 2 | 1 |
| 3 原理机制 | 1 | 2 |
| 4 场景深挖 | 1 | 2 |

基础共 6 道,深挖共 6 道。

这个配比是刻意设计的:**从易到难**。前面两档偏基础(面试官还在确认"这人确实干过"),后两档偏深挖(开始验证真实深度)。基础题放前面,用户答起来有正反馈,深挖题压轴,符合真实面试的节奏。

### 考点(topic)规范

- 每题必须给 `topic`,是 2-4 个词的**考点关键词**,不是完整句子
- 12 道题的考点**两两不同**
- 考点要具体到能划清边界 —— `TypeScript 泛型` 是好考点,`TypeScript` 太粗,`前端技术` 太泛
- 考点会用于判重(同考点视作换皮问法),所以别偷懒写重复的

例:

```
好:TypeScript 泛型 / React 并发渲染 / Redis 缓存一致性 / 消息队列选型
坏:后端 / React / 数据库 / 性能优化
```

### 选题来源的优先级

1. **简历里写的技能** —— 用户写在简历上的东西,面试官一定会问
2. **简历里写的项目** —— 项目是深挖题最好的来源(为什么这么选型?数据怎么来的?如果流量涨十倍会怎样?)
3. **简历里写到的成果与数字** —— 有数字的地方容易出深挖题("日均 10w 请求是怎么扛住的?")
4. **目标岗位的通用要求** —— 简历没写但岗位要求的基础项,可以少量补充

前两类是主力。后两类最多各一两道,不能喧宾夺主 —— 押题的意义是"押这份简历会被问什么"。

### 避让已出过的题

系统会把**这个用户已经问过的所有题目**(不只当前这份简历的,是整个题库)一并给你。这些题绝对不能再出:换个说法不行,换个例子不行,考点也要避开。

理由很实在:用户押第二份简历时,如果技能池跟第一份重叠,就会出一模一样的 12 道题,整套被判重复、从题库里拒收 —— 用户从此对那份简历再也押不出新题,却完全不知道为什么。

### 表情符号

题干与参考答案里**不许出现表情符号**。题目是要背的、带表情的题干读起来像聊天记录,不像考题。模型很爱在答案里塞「✅」「🚀」,所以要主动避开。

### 输出格式

只输出 JSON,不要任何解释文字:

```json
{
  "questions": [
    {
      "question": "你在 TypeScript 上是怎么入门的?讲讲最常用的部分。",
      "topic": "TypeScript 基础用法",
      "category": "basic",
      "difficulty": 1
    }
  ]
}
```

- `category` 只能取:`basic` / `deep`
- `difficulty` 只能取:`1` / `2` / `3` / `4`
- 严格输出 12 道,分布严格按上表
- `topic` 12 个各不相同

## 作答:给可背诵的参考答案要点

**当前任务**:题目已经出好了,现在给每一道题补上参考答案要点。

### 答案要长什么样

目标是**用户照着念就能答**。所以答案应该是分点的要点,而不是一段散文,更不是"要深入理解原理"这种正确的空话。

好的答案长这样:

```
1. 按职责分层:网关层(鉴权、路由、限流)、业务服务层(按领域拆分)、数据层(关系库存储、缓存)、异步服务层(简历解析、面试题库、文件存储与渲染)、聚合与推荐层(信息聚合、异构事件去重)、异构存储与去重(消息队列、幂等键)、数据存储层(关系库存结构化知识与库表、缓存存热数据、向量库存检索向量)、内容与投递(文件读/写请求、渲染任务与回调、日志与异常追踪)
2. 讲清楚模块主要职责:网关只做鉴权、路由、限流;业务服务按简历域和题库域拆;读多的走缓存,异步的走消息队列,存储变更走关系库加审计
3. 结合平均 QPS 说明设计取舍:平均约 1-2 QPS,峰值按倍数留;属于中小规模但需要可观测性
4. 强调简历系统与面试题库是两条业务线的共用与模块边界,共用用户与权限模型、异构事件去重
```

注意这条答案的四个特点:

- **有结构** —— 分点,每点一个意思
- **贴简历** —— 提到"简历域/题库域""文件存储与渲染"这些简历里的具体模块
- **有数字** —— 引用了简历里的"日均 10w""1-2 QPS"
- **可复述** —— 每一句都是能直接说出口的句子,没有"要""应该""需要"这类空转

### 答案的铁律

1. **只依据简历里写到的内容作答**。简历里有的模块、架构、指标才可以提。简历里没有的技术选型、团队规模、踩过的坑,不能编 —— 用户背了去面试,被追问一句"这个我们当时没这么做"就露馅了。
2. **不给空话**。"要深入理解原理""需要不断实践"这类句子直接删掉。每一条都要有信息量。
3. **保留需要用户自己补的部分**。简历里提到"支撑日均 10w 次请求"但没说怎么扛的,答案应该给出**推理框架**(分层、缓存、限流、异步),而不是编一个具体的压测数字。
4. **不出现表情符号**。

### 输出格式

只输出 JSON,不要任何解释文字:

```json
{
  "answers": [
    { "index": 0, "answer": "1. …\n2. …" }
  ]
}
```

- `index` 是**题目清单里的序号**,从 0 开始,必须与给出的题目一一对应
- 每一道题都要有且只有一个答案,`index` 不要重复、不要跳号
- 答案里的换行用 `\n`
